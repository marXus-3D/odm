A download manager that keeps every connection busy

Notes on how DM pulls one file over eight sockets, why that is faster, and why the browser should be the one handing it the link.

Written in Go for WindowsVersion 0.1.12Download DM-Setup.exe

Your browser downloads a file over one connection, and most servers cap what one connection may have. That is the whole story of why download managers exist. Open eight connections to the same file and you have eight times the ceiling, and eight shares of any busy link along the way, because TCP divides a bottleneck per flow rather than per person.

DM does this, and one more thing that turns out to matter as much: it decides how to split the file while the download is running, not before.

The trouble with fixed chunks

The obvious approach cuts the file into eight equal pieces and hands one to each connection. It works until one connection is slower than the others, which is nearly always. Seven connections finish their eighth and then sit idle while the slow one grinds through its share. The slowest socket decides when you are done.

DM begins with a single range that covers the whole file. Whenever a connection has nothing to do, it looks for the largest range still in progress, splits what is left of it in half, and takes the tail. The same small routine performs the initial fan-out in the first few milliseconds and the rebalancing near the end. A connection that is slow simply keeps having its territory split away from it, and it ends the transfer owning a sliver.

Where the bytes go

Each range writes straight into the final file at its own offset. The file is created at its full size first, so there are no temporary part files and no merge pass when the last byte lands. The download is finished the instant the last range is.

Finished ranges are recorded as they complete. That record is what makes resume exact: close the app, restart the machine, lose the network for an hour, and the download continues from the byte it stopped at rather than from the last checkpoint it happened to reach.

Streaming video works the same way at a different grain. An HLS playlist is a list of short segments; DM fetches them as ranges of one logical file and, if ffmpeg is on the machine, writes a single MP4 at the end.

Why the browser should hand it over

A download manager that has to be fed links by hand is a download manager you stop using. The DM extension watches for downloads inside Chrome, Edge, Brave or Vivaldi and passes each one to the app through the browser's own native-messaging channel, together with the cookies for that site. A file behind a login downloads the way it would have in the browser, only faster. Pages with streaming video get a small button that sends the stream across.

The app itself is a native Windows window, dark, with a tray icon, a save-as dialog when a download arrives, a progress dialog while it runs, and a dialog when it finishes. If you would rather have a browser tab, the same list is served on localhost, and there is a command line for scripts.

What it costs the machine

  • About 9 MB of memory when idle. The background service is a single Go binary with no third-party modules.
  • Nothing at startup unless you ask. Running at sign-in is a checkbox in the installer, and one in the app.
  • Nothing outside your user folder. The installer needs no administrator prompt and the uninstaller leaves your download list in place unless you tell it otherwise.
